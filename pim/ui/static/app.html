PIM

What this stage does It writes the brand's setup files (the YAML on the right). You answer five things, in order, and the checklist on the right tells you what is still missing.
  1. Brand — who it is and where its files live.
  2. Files — which files to read, and for each one: the sheet, the row with the column headings, and the column holding the part number (the file is lined up on it).
  3. Columns to keep — tick the columns you want and give each a name. Everything you don't tick is ignored.
  4. Roster — which file's part-number list defines "the products". Other files only add information to those.
  5. Validate → Save pack, then Build (dry run) to see coverage before anything is stored.
Next: once the checklist is all ticked and a Build (not a dry run) has succeeded, go straight to 4 Decide. Skip 2 What changed the first time — it is for later, when the brand sends you an updated file.

3Columns to keep

How to fill this in
  1. Tick a column to keep it. A suggested name appears; change it if you like (letters, digits, underscores — this is the name you'll see everywhere after this).
  2. Type: text unless the column is a number, a true/false, HTML, or a web link. Numbers that are really codes (EANs, part numbers) stay text so leading zeros survive.
  3. Unit: if the column's heading says the unit (Length (mm)) it is filled in for you. If the unit is inside the values (133.5 mm, 4,72 in) type the units it may contain, comma-separated: mm,in.
  4. Fallback for: the same information from a second file. Pick the field you already named; this column fills in only where that one is empty. If both have a value and they disagree, the build stops and shows you both.
  5. req and publish never remove a column — ticking the column is what keeps it. req = every product must have a value; if one is blank the build stops and names the product (use it for the part number and title). Unticked, blanks are allowed and the build just reports how many. publish = the value is sent to the store when you publish. Unticked, it stays in your database for your own use and the store never sees it (vendor cost, internal notes).

4Which file is the product list?

Your files don't all list the same part numbers (a price book has codes that were never catalogued; a scrape misses some). The pipeline needs one answer to "which part numbers are the products?" — pick the file whose list is the product list. Every other file only adds columns to those products; a part number that is in another file but not in this one is reported, not added.

If the price list uses different codes than the catalog for the same product (HS8147 vs 8147), those pairs go in joins.yaml → associations; the window shows them but does not edit them yet.

5Save and check

Validate checks the setup for mistakes. Save pack writes brands/<name>/. Build (dry run) reads your files and reports coverage; it stores nothing.

    How a change flows through
    1. A file changes in the brand folder (new price book, corrected sheet, a scrape rerun).
    2. What changed shows it as changed or new — nothing has happened to your data yet.
    3. Build makes a new numbered version. Your overrides and decisions are re-applied on top; if a value you ruled on moved underneath, the build says so instead of guessing.
    4. Compare two builds to see exactly which products and fields changed, before → after.
    5. Later: Publish shows the same diff against the live store before any write, and every run can be rolled back.
    What this stage does A build reads the files, lines every product up by part number, fills gaps from fallback columns, applies your overrides, and stores a numbered version. Dry run does all of that but stores nothing — use it first. Then Compare two versions to see exactly what changed. Every number shown is measured, and a FAIL names the product and field.     How the decision sheet works
    • One row per CT SKU: every vendor part number, each pack under its parent, kits at the end.
    • You fill in the shaded columns in Excel: carry_state (carry, skip, or derivatives-only / carry+derivatives when a row gets packs or kits), and optionally hold_reason, fulfillment, initial_qty, a hand-set price (beats every rule) and new_pack_qty (5 or 5;10) to add packs.

    • Preview checks every cell and refuses the sheet while any error stands. Apply writes decisions/decisions.csv (and derivatives.csv for new packs). Build again so the catalog reflects it.
    • Packs: N × each for cost, list and weight; dimensions are never computed. Kits are set in derivatives.csv (kit,,,MS-KIT5,MSEF:1;MSF:2;MSM:1;MSL:1,…) and sum their components. Pricing rules live in pricing.yaml.
